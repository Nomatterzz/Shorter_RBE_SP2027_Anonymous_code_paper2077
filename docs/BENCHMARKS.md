# Benchmark protocol and interpretation

The submitted raw results were generated by `scripts/benchmark.py`. That script
runs independent processes for each preset. Each process creates fresh public
parameters and prepares its public NTT matrices, then performs the requested
number of trials with fresh user keys and encryption randomness. There is no
private-randomness preprocessing. The current backend is single-threaded.

Each trial registers actual keys through the binary-counter update algorithm.
The per-registration times include rebuilding destination trees with their new
terminators. The first-user witness, encryption and decryption are measured after
those updates. No step of a merge or Gaussian sampler is replaced by a constant
or skipped to improve timings. The decryption code verifies the resulting
plaintext in every trial.

Reported separately:

- setup and public NTT preparation;
- key generation, every registration, total registration and witness generation;
- witness and ciphertext serialization;
- encryption including randomness, Gaussian sampling and exact quantization;
- ciphertext parsing and exact-CRT decryption;
- process peak RSS, compact object sizes, public log size, live/rebuilt nodes;
- Gaussian and quantizer counts, rejection counts and encryption RNG bytes.

Memory is Linux getrusage(RUSAGE_SELF).ru_maxrss in KiB. It is a process high-water
mark and includes setup/cached public transforms, keys, registry, current trial
ciphertexts and temporary buffers. It is not isolated per-function live memory.
The operating environment is recorded without hostname or personal paths. Shared
CPU scheduling, frequency changes and allocation state affect absolute times.
Three or five trials are useful reproducibility checks, not a claim of exhaustive
statistical characterization. Consult every raw trial and standard deviation.

The configured large registration capacity fixes the number of slots. It does
not allocate a billion users. The result metadata records the actual registry
population, by default four. Run a real scaling study, for example:

```sh
for USERS in 1 2 4 8 16 32; do
  python3 scripts/benchmark.py --binary build/rbe_cli --presets main two-independent \
    --users "$USERS" --iterations 3 --out-dir "results/scaling-$USERS"
done
```

Registry costs depend on shared identity prefixes. Full presets use deterministic
SHA-256-derived application identities for reproducibility, while keys and encryption
coins are fresh CSPRNG outputs. These timings are not adversarial worst-case bounds.
For toy, identities use small counters to exercise merges inexpensively.

## Fair comparison

`matched` and both retuned two-coordinate instances use 30 slots, the same source
ring, rank, q, key distribution law, source Gaussian width, statistical target,
quantizer and implementation backend. Their encryption noise and transmission
precisions differ exactly as in the paper's parameter choices. The original
KLSS Rust program was not run. Its published times are not imported into our
summary, and no cross-implementation speedup is claimed.

The `main` instance has 31 slots to include the exact 2^30-registration boundary.
It is not silently substituted for the 30-slot instance in the 34.3% comparison.
The 36.7% comparison is against the radix-restricted control, not the independently
retuned stronger control. Source instance sample counts differ and are reported.

The benchmark times the in-memory algorithm API, not the persistent CLI startup,
log replay or filesystem I/O. The CLI deliberately reconstructs its registry from
the public log on startup. Filesystem workflow correctness is separately tested.

The submitted Release build uses the default CMake Release compiler flags, without `-march=native`, LTO, or private-data preprocessing. `results/scaling-16` is a separate small-population scaling measurement, not a replacement for a large-registry study.
